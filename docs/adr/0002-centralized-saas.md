# ADR-0002: Централизованный multi-tenant SaaS

| Поле   | Значение   |
| ------ | ---------- |
| Статус | принято    |
| Дата   | 2026-11-15 |

## Контекст

Клиент не должен ставить сервер, открывать терминал и сопровождать инфраструктуру.
Вендор продает подписку и ведет клиентов. При этом данные разных клиентов
должны быть изолированы, а вендор не должен видеть сырые данные активности
разработчиков.

## Решение

- Один центральный инстанс в регионе РФ; мультитенантность на уровне БД.
- `tenant_id NOT NULL` во всех тенант-таблицах + PostgreSQL RLS +
  `SET LOCAL app.tenant_id` в транзакции.
- API выбирает tenant из сессии/токена, никогда из тела запроса.
- Вендорская роль работает через ограниченные представления: финансы,
  лимиты, воронка онбординга; без сырых heartbeat и без кода.
- Отдельные контуры: вендорский (`customers`, `invoices`, `payments`,
  `provisioning_packages`) и тенантский (`users`, `memberships`,
  `projects`, `day_records`, …).

## Последствия

- Плюс: единый онбординг, биллинг, обновления и наблюдаемость.
- Минус: критичность изоляции; нужны тесты на чтение/запись чужого tenant по
  каждому ресурсу и пентest.
- Минус: данные клиента хранятся у вендора — требуется DPA, согласие и
  проверка 152-ФЗ.

## Альтернативы

- Self-host: отвергнут в MVP (сопровождение каждого клиента).
- Отдельная БД на клиента: дороже в эксплуатации при малом числе клиентов;
  вернуться при enterprise-запросах.
