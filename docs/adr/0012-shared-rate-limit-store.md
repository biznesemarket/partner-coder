# ADR-0012: Общий rate-limit store в PostgreSQL

| Поле      | Значение                               |
| --------- | -------------------------------------- |
| Статус    | принято                                |
| Дата      | 2026-11-15                             |
| Связанные | ADR-0009, ADR-0010, ADR-0011, M6, R-41 |

## Контекст

Per-email лимит OTP/magic-link (5/мин) и собственный лимит Better Auth жили
в памяти процесса. При двух и более API-инстансах каждый процесс считал
попытки отдельно: клиент получал N × лимит, а распределенный перебор OTP
становился дешевле. Redis в MVP не используется — очереди уже живут в
PostgreSQL (pg-boss), и отдельная инфраструктура не нужна.

## Решение

1. **Better Auth хранит rate limit в БД вне local.** При
   `RATE_LIMIT_STORAGE=database` включается `rateLimit.storage = "database"`;
   модель `rateLimit` маппится на таблицу `auth_rate_limits` (`key`, `count`,
   `last_request`). Значение по умолчанию вычисляется из `APP_ENV`: local —
   memory, staging/prod — database; переменная окружения может переопределить
   выбор.
2. **Per-email лимитер использует `email_rate_limits`.** Один атомарный
   `INSERT … ON CONFLICT DO UPDATE` увеличивает счетчик и сбрасывает окно;
   все инстансы видят один лимит. Ключ — нормализованный email, окно —
   фиксированное (60 секунд, 5 попыток).
3. **Роли разделены.** `auth_rate_limits` доступна только
   `partner_coder_auth`; `email_rate_limits` — только `partner_coder_api` и
   worker для очистки. Обе таблицы глобальные (без `tenant_id`), RLS включен,
   политика разрешает доступ только владельцу контура.
4. **Сбой БД не блокирует вход.** Database-лимитер при ошибке пишет warning и
   использует memory-fallback текущего инстанса; Better Auth при недоступной
   БД все равно не сможет аутентифицировать пользователя.
5. **Retention.** Worker удаляет строки старше суток вместе с остальными
   TTL-задачами; счетчики не являются аудитными данными.
6. **Глобальный лимит Fastify остается per-instance.** 300 запросов/минуту —
   защита от всплеска на инстансе; распределенный лимит на уровне edge/WAF
   добавляется при выборе хостинга. Чувствительные auth-маршруты защищены
   общим store.

## Последствия

- Каждый запрос к `/api/auth/*` и каждая попытка OTP/magic-link выполняют
  дополнительную запись в PostgreSQL. Это приемлемо на фоне существующих
  запросов аутентификации и снимает риск N × лимит.
- Managed PostgreSQL runbook должен выдавать гранты на новые таблицы
  (миграция делает это для ролей, созданных миграциями).
- Таблицы растут ограниченно: ключи — IP+путь и email; worker чистит их
  ежечасно.
- При нескольких БД (шардирование) счетчик придется выносить в общий сервис;
  в MVP одна managed PostgreSQL.
