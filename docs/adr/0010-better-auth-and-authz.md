# ADR-0010: Better Auth, приглашения и матрица авторизации

| Поле      | Значение                           |
| --------- | ---------------------------------- |
| Статус    | принято                            |
| Дата      | 2026-11-15                         |
| Связанные | ADR-0002, ADR-0006, ADR-0009, M2.2 |

## Контекст

M2.1 создала схему, RLS и роли БД, но не было входа пользователей, проверки
прав и выдачи агентских токенов. Нужен self-hosted вход без внешнего IdP,
одноразовые приглашения, ограниченные device-токены и единая матрица
«роль × ресурс × действие» для API. Требование ADR-0006: passkeys и 2FA
появятся позже, но схема должна быть готова.

## Решение

- Better Auth 1.7 с Drizzle-адаптером; email OTP и magic link. Токены magic
  link хранятся SHA-256-хешем; OTP — HMAC-SHA-256 с `AUTH_SECRET` (6 цифр нельзя
  защитить быстрым неключевым хешем).
- Better Auth работает под отдельной ролью `partner_coder_auth`, у которой
  есть доступ только к `users`, `auth_sessions`, `auth_accounts`,
  `auth_verifications` (и будущим `auth_two_factors`, `auth_passkeys`).
  API-роль `partner_coder_api` не видит секреты `auth_accounts`/
  `auth_verifications`/2FA/passkeys; `users`/`auth_sessions` доступны ей только
  через RLS для собственных строк. Вне `local` сервис
  проверяет при старте, что логины не суперпользователи, не `BYPASSRLS` и не
  состоят одновременно в auth- и API-ролях; иначе не стартует.
- `users` — глобальная таблица; доступ к tenant определяется членством
  `memberships` и RLS. Сессия может хранить активный tenant; API принимает
  tenant только из сессии или device-токена, но не из тела запроса.
- Приглашение: 256-битный токен, в БД только SHA-256-хеш, TTL, одна
  активация, отзыв. Принятие требует аутентифицированного пользователя с
  совпадающим подтвержденным email. Существующее членство не активируется
  повторно и не меняет роль: для этого нужно явное действие director. Director
  может пригласить любую роль, support — только developer; иначе support
  выдал бы себе director/finance.
- Device-токен: 256-битный секрет с префиксом `pcd_`, в БД только SHA-256,
  TTL по умолчанию 90 дней, scope, отзыв и ротация с записью `rotated_from`.
  Выпуск и ротация — только из веб-сессии; ротация сохраняет срок и доступна
  только владельцу токена. Токен привязан к tenant, членству и, опционально,
  устройству; отозванное устройство и приостановленный tenant токен не
  пропускают. Отзыв каскадно закрывает цепочку `rotated_from`. До появления
  агентских маршрутов device-токен ходит только в `/v1/auth/me` и может
  отозвать себя.
- Авторизация: чистая матрица в `@partner-coder/contracts`; Fastify-middleware
  проверяет роль, tenant и право. Отказ пишется в `tenant_audit_events` через
  `app_audit()`; отказ пишется отдельной транзакцией, чтобы падение операции
  не откатывало запись; чужой tenant запрещен раньше ролевой проверки.
  Приостановленный (`suspended`) или архивный (`archived`) tenant не дает
  активного контекста.
- Better Auth-таблицы ID: пользователи/сессии — UUID (`advanced.generateId`),
  служебные таблицы плагинов — text, потому что Better Auth генерирует
  собственные идентификаторы для verification.

## Последствия

- Плюс: нет внешнего identity-вендора; OTP/magic-link токены не лежат в БД
  открытым текстом; device-токены хешируются и ограничены сроком.
- Минус: Better Auth хранит токен сессии в `auth_sessions.token` открытым
  текстом — это дизайн библиотеки; доступ ограничен ролью `partner_coder_auth`
  и RLS. При компрометации БД сессии нужно отзывать.
- Минус: rate limit Better Auth сейчас в памяти процесса; для нескольких
  инстансов нужен общий store (M2.3). Клиентский IP берется из заголовка,
  который должен перезаписывать edge; `AUTH_IP_HEADERS`/`AUTH_TRUSTED_PROXIES`
  задают доверенную цепочку. Лимита на email пока нет.
- Passkeys/2FA: схема `auth_passkeys`/`auth_two_factors` создана, плагины
  включаются отдельным изменением без миграции таблиц.
- HMAC-ключ аудита вне БД по-прежнему не сделан (см. ADR-0009).

## Альтернативы

- Собственная реализация OTP/сессий: больше кода и риск ошибок в
  криптографии/одноразовых токенах.
- Внешний IdP: данные и зависимость за рубежом, противоречит выбранному
  хостингу.
