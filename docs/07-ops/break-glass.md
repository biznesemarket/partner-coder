# Break-glass: восстановление доступа суперадминистратора

Статус: утверждено 2026-11-19.

## 1. Когда применять

Только если **ни один** активный суперадминистратор не может войти в консоль:

- потерян пароль и нет доступа к почте;
- потерян TOTP/passkey и нет второго администратора;
- учётная запись заблокирована, а другого активного суперадминистратора нет.

Не применять для обычных сбросов, конфликтов ролей или просьб «быстрее
проверить». Обычный сброс MFA делает другой суперадминистратор через
`POST /v1/vendor/users/:id/reset-mfa`.

## 2. Кто имеет право

- Владелец ООО «ФОНИИ» или лицо, письменно им уполномоченное.
- Технический администратор с доступом к серверу и базе.
- Желательно два человека: один выполняет, второй подтверждает и фиксирует.

Пароли и ключи не передаются в чатах. Доступ — через менеджер секретов и
SSH-ключи.

## 3. Подготовка

До аварии должно быть готово:

- SSH-доступ к серверу под отдельным ключом;
- доступ к `DATABASE_URL` мигратора/администратора в менеджере секретов;
- работающий SMTP или резервный канал доставки письма;
- доступ к журналу аудита;
- телефон владельца для подтверждения личности.

## 4. Процедура A: временный суперадминистратор

1. Подтвердить личность владельца по телефону/видео.
2. Зафиксировать инцидент: дата, время, кто выполняет, причина.
3. На сервере выполнить:

   ```bash
   pnpm --filter @partner-coder/api vendor:admin -- \
     --email breakglass@pcoder.ru \
     --name "Break glass" \
     --force
   ```

4. Открыть письмо со ссылкой сброса, установить пароль, включить TOTP,
   добавить passkey.
5. Войти в консоль и проверить, что это действительно суперадминистратор.
6. Восстановить доступ основного администратора:
   - сбросить MFA через `POST /v1/vendor/users/:id/reset-mfa`;
   - отправить ссылку сброса пароля;
   - при необходимости изменить статус на `active`.
7. После входа основного администратора:
   - отозвать сессии временного аккаунта;
   - установить временному статус `disabled`;
   - проверить журнал аудита.
8. Записать итог инцидента и причины.

## 5. Процедура B: аварийное вмешательство в БД

Применять, только если процедура A невозможна (нет SMTP, CLI не запускается,
аккаунт повреждён). Требуется подтверждение владельца и второй человек.

1. Сделать свежий backup БД.
2. Подключиться под администратором БД.
3. Для выбранного суперадминистратора:
   - удалить его сессии;
   - удалить TOTP/passkeys;
   - убедиться, что статус `active` и роль `superadmin`.
4. Выполнить сброс пароля штатным способом; если почта недоступна —
   использовать временный пароль через поддерживаемый Better Auth механизм,
   а не писать произвольный хеш вручную.
5. Войти, включить TOTP/passkey, сменить пароль.
6. Отозвать временные сессии, проверить аудит.
7. Ротировать `VENDOR_AUTH_SECRET`, если есть подозрение на компрометацию.

Точные SQL-команды выполняются только после проверки на копии БД. Не
отключать RLS, не выдавать superuser runtime-логинам и не коммитить пароли.

## 6. После восстановления

- Проверить `verify_vendor_audit_chain()`.
- Проверить, что активен ровно один суперадминистратор.
- Временно оставить временный аккаунт `disabled`, не удалять сразу: он нужен
  для аудита.
- Записать инцидент в журнал эксплуатации.
- Пересмотреть, нужен ли второй постоянный администратор.

## 7. Ограничения

- Break-glass не является постоянным вторым администратором.
- Не использовать для обхода MFA в обычной работе.
- Не хранить резервные коды в репозитории или чате.
- Не выполнять без backup и аудита.
